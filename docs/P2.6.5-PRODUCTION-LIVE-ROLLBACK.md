# P2.6.5 — Production LIVE Rollback / Failed Activation Recovery

## Purpose

P2.6.5 completes the Production safety cycle by providing an audited, atomic recovery path for a **committed P2.6.4 LIVE activation**.

It does not guess what “safe” should look like. P2.6.4 already stored the exact pre-LIVE snapshot, and P2.6.5 restores that snapshot.

## Recovery boundary

The target is the exact P2.6.3 certified-dark state that existed immediately before LIVE:

- Production hotel becomes inactive again;
- public identity returns to `certified`;
- property lifecycle returns to `draft`;
- published revision stays the same exact certified revision;
- previous `last_known_good_revision_id` is restored;
- projection status/metadata are restored exactly;
- revision validation JSON is restored exactly;
- P2.6.3 health certification remains `healthy / passed` for the same revision.

Because the LIVE relational UUID bridge requires the P2.6.4 LIVE marker plus active hotel/identity state, restoring the snapshot automatically disables Production relational authority without widening the old M10 normalized runtime.

## Failed activation semantics

P2.6.4 is one database transaction. If it fails before COMMIT, PostgreSQL already rolls the entire activation back and P2.6.5 has nothing to undo.

P2.6.5 is for a LIVE activation that **did commit** and must later be withdrawn because of runtime, operational, configuration or launch problems.

The recovery RPC also tolerates a partially restored lifecycle only when every mutable field is either:

1. the exact P2.6.4 LIVE value; or
2. the exact immutable pre-LIVE snapshot value.

Any third state is treated as unsafe drift and recovery stops instead of overwriting unrelated changes.

## Immutable recovery ledger

`factory_production_live_rollback_runs` is append-only and unique by `live_activation_run_id`.

It records:

- actor;
- exact P2.6.4 activation target;
- public slug;
- human rollback reason;
- deterministic rollback hash over target, checks, evidence and approval;
- the exact restored snapshot values;
- timestamp and final status `rolled_back_certified_dark`.

The P2.6.4 activation ledger is never updated or deleted. Activation and rollback remain separate immutable historical facts.

## Idempotency

Retrying the exact same rollback request returns the existing rollback run only if the database is still exactly at the restored snapshot.

A different reason, hash, target, checks or approval for the same activation run is rejected as an idempotency conflict.

After rollback, replaying the old P2.6.4 activation request cannot silently reactivate the hotel: the P2.6.4 ledger replay path requires the LIVE state and therefore fails closed once the snapshot has been restored.

A future reactivation must run through a new explicit controlled lifecycle, not stale evidence.

## What rollback does not change

P2.6.5 does not:

- delete or supersede the published revision;
- revoke the P2.6.3 certification evidence;
- create, rotate, deactivate or delete staff PINs;
- enable/disable factory services, workflows, integrations or role templates;
- mutate normalized routing resources;
- touch another hotel;
- create a fake Product Factory tenant.

Operational resources are required to remain fail-closed before the recovery mutation.

## Security

The rollback RPC is:

- `SECURITY DEFINER`;
- fixed to `search_path = pg_catalog, public`;
- executable only by `service_role`;
- reachable from the application only through an authenticated, same-origin Control Plane POST by active `super_admin` or `operator` authority.

The rollback ledger has RLS enabled and grants application service authority only `SELECT + INSERT`.

## P2.6.4 advisor follow-up

P2.6.5 adds the covering partial index for `factory_production_live_activation_runs.previous_last_known_good_revision_id`, the nullable rollback FK that the Supabase performance advisor flagged after P2.6.4.

## Current validation rule

The current database has zero Product Factory onboarding/publication/certification/activation rows. Therefore implementation validation must leave:

- all P2.1–P2.6.5 factory run rows at zero;
- LIVE activation and rollback audit events at zero;
- all Product Factory config/envelope rows at zero;
- the hotel registry unchanged;
- existing staff credentials unchanged.

Neither activation nor rollback RPC is invoked merely for platform testing.
