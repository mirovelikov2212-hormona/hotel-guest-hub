# P4.3 — Audited Draft Foundation Creation

Status: **exact-preflight-gated P2.1 tenant foundation creation**

## Goal

P4.3 turns the completed bilingual blueprint workspace into the first intentional Hotel Factory write action without making any new hotel runnable.

After an operator completes the five-step blueprint and receives a successful Product Factory preflight, the workspace may create the existing P2.1 foundation transaction:

- one draft Property;
- one inactive Production hotel identity;
- one inactive Sandbox hotel identity;
- both registered environments;
- draft revision 1 for each environment;
- one immutable onboarding run and Control Plane audit event.

No later Product Factory stage is chained automatically.

## One mutation authority

P4.3 does not introduce a second onboarding transaction or RPC. The existing `beginFactoryOnboarding` service and `begin_factory_onboarding_v1` database function remain the sole tenant-foundation mutation authority.

The existing `/api/control-plane/onboarding` route is hardened so all HTTP callers now require the P4.3 preflight/approval contract. This avoids leaving a weaker legacy mutation endpoint beside the wizard.

## Exact preflight binding

The create request includes:

- the complete blueprint;
- the blueprint hash returned by the successful preflight;
- one explicit idempotency key;
- the exact draft-only approval object.

Before any database mutation, the server reruns `prepareFactoryOnboarding`, including blueprint normalization, Product Factory validation and embedded-secret rejection. The recomputed hash must equal the approved preflight hash. A mismatch returns `stale_preflight` and never invokes P2.1.

The browser also binds the visible create panel to a JSON snapshot of the successful preflight blueprint. Editing any blueprint field hides the create action and requires a new preflight. This is a UX guard only; the independent server hash comparison remains authoritative.

## Explicit approval

The HTTP mutation requires exactly:

- `createDraftTenant = true`;
- `keepProductionInactive = true`;
- `keepSandboxInactive = true`;
- `publishRevision = false`;
- `activateLive = false`.

Extra or changed approval fields are rejected.

## Idempotent retry

The create panel generates one idempotency key when it mounts for one exact successful preflight. The key is intentionally retained after transient/network failure.

If the P2.1 transaction committed but the response was lost, a retry uses the same key and the existing database idempotency contract returns the original onboarding run instead of creating another Property or hotel pair.

## Result state

A successful P4.3 response explicitly reports the fail-closed foundation state:

- property lifecycle `draft`;
- Production inactive;
- Sandbox inactive;
- revision unpublished;
- LIVE activation false.

The UI shows the immutable onboarding run ID, Property ID and Production/Sandbox hotel IDs.

## Deliberate boundary

P4.3 does **not** automatically invoke:

- P2.2 core-resource projection;
- P2.3 operational-resource projection;
- onboarding envelope projection;
- Sandbox certification;
- Production readiness/publication/runtime certification;
- LIVE activation;
- commercial trial/customer state.

Those transitions remain separate audited Product Factory actions.

## Validation policy

P4.3 validation must never create a fake hotel. Source contracts, build/Preview evidence, existing P2.1 transaction contracts and read-only Supabase invariant checks are used. The onboarding POST is not invoked during validation because the current Product Factory registry intentionally contains no disposable tenant.
