# P2.1 — Automated Hotel Onboarding Transaction Foundation

Status: **first Product Factory mutation foundation**

## Goal

P2.1 turns the P0 blueprint contract into one controlled, idempotent database
transaction without making a new hotel live.

This stage deliberately does **not** project rooms, departments, services,
workflows, integrations, reporting, branding or knowledge into runtime tables.
Those resources are added by the following P2 stages after the transaction
boundary is proven.

## What one successful P2.1 transaction creates

For one validated factory blueprint:

1. reuses or creates the organization identity;
2. creates one draft property;
3. creates one inactive Production hotel runtime identity;
4. creates one inactive Sandbox hotel runtime identity linked to Production;
5. registers both environments in `property_environments`;
6. creates revision 1 as a draft for each environment;
7. records one immutable onboarding run;
8. appends one Control Plane audit event.

Production and Sandbox are therefore real isolated tenant identities from the
first transaction, but neither is activated.

## Fail-closed revision state

The initial revisions use `source_type = factory_blueprint` and contain the
validated normalized blueprint under a P2.1 wrapper.

Their validation state is intentionally:

- `ok = false`;
- error `FACTORY_BLUEPRINT_NOT_PROJECTED`;
- warning `P2_1_FOUNDATION_ONLY`.

P2.1 never publishes a revision and never activates either hotel. A later stage
must project and validate the complete runtime configuration before Sandbox
certification and publication can begin.

## Idempotency

Every onboarding request supplies an explicit idempotency key and a deterministic
SHA-256 hash of the normalized blueprint.

The database transaction takes an advisory transaction lock for that key.

- same key + same blueprint hash: returns the original run and tenant IDs with
  `replayed = true`;
- same key + different blueprint hash: fails with
  `P2_FACTORY_IDEMPOTENCY_CONFLICT`;
- a retry can never create a second property or second pair of hotel environments.

A second advisory lock protects the organization/property identity while the
transaction is creating it.

## Authority boundary

The HTTP mutation path is Control Plane only:

- same-origin POST;
- valid independent Platform Admin session;
- role must be `super_admin` or `operator`;
- no Hotel Manager PIN or staff session authority;
- request body is size-limited;
- embedded credentials/secrets are rejected before persistence.

The database RPC is executable only by `service_role` and rechecks the exact
active Platform Admin role before writing.

## Database authority and audit

`factory_onboarding_runs` is RLS-enabled and unavailable to `anon` and
`authenticated`. Application service authority receives only SELECT + INSERT;
there is no normal update/delete path for completed onboarding history.

The transaction appends `factory_onboarding_foundation_created` to the existing
append-only `control_plane_audit_log`.

## P2.1 exit criteria

P2.1 is complete when:

- P0 blueprint validation still passes;
- deterministic blueprint hashing and derived identities are contract-tested;
- secrets are rejected;
- migration contracts prove idempotency and fail-closed Production/Sandbox
  creation;
- the new Control Plane RPC receives explicit tenant-isolation review;
- the full contract suite and tenant-isolation gate pass;
- Next.js production build passes;
- an exact Vercel Preview for the P2.1 head is READY;
- the migration is applied and its RLS/grants/function authority are verified.

A non-production certification blueprint may then be used to prove exact replay
behavior before P2.2 starts projecting rooms and departments.
