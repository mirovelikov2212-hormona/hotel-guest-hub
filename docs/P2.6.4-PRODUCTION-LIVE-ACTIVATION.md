# P2.6.4 — Production LIVE Activation Transaction

## Purpose

P2.6.4 is the first Product Factory stage that is allowed to make a **real, previously certified Production tenant publicly reachable**.

The stage is deliberately narrower than “turn everything on”. It transitions the certified Production identity into a LIVE **pilot** while preserving the exact P2.6.3 published revision as semantic runtime authority. Factory operational resources that have not been separately configured remain fail-closed.

No activation is executed merely to test this platform code. A real activation requires a real immutable P2.6.3 certification run.

## Required lineage

The activation RPC rechecks the complete immutable chain:

`P2.1 onboarding → P2.2 core resources → P2.3 operational drafts → P2.4 envelope → P2.5 Sandbox certification → P2.6.1 Production readiness → P2.6.2 dark publication → P2.6.3 runtime certification → P2.6.4 LIVE`

The P2.6.3 certification must match the exact:
- Production hotel;
- Production revision;
- certified Vercel deployment id;
- certified 40-character Git SHA.

## LIVE transition

One transaction performs CAS-protected changes:

- `hotels.active: false → true`;
- `hotel_public_identity_configs.status: certified → active`;
- `properties.lifecycle_state: draft → pilot`;
- `hotel_config_publication_state.last_known_good_revision_id` becomes the exact certified published revision;
- revision validation moves from `FACTORY_PRODUCTION_RUNTIME_CERTIFIED_DARK` to `FACTORY_PRODUCTION_LIVE_PILOT`;
- projection metadata records P2.6.4 LIVE state.

The exact revision stays `published`. Health stays `healthy / passed` for that revision.

The hotel registry flag is the actual Guest/QR/Staff reachability switch. All changes are committed atomically.

## Published-config authority and relational IDs

Existing Production behavior intentionally does **not** use the M10 Sandbox normalized-runtime activation path.

P2.6.4 preserves that boundary:
- published configuration remains semantic authority for rooms, service definitions, department routing, hours and guest behavior;
- `routing_rules.active` remains false;
- M10 room/department normalized runtime activation remains Sandbox-only;
- factory services/workflows/integrations/role runtime remain disabled.

A Product Factory hotel with custom departments still needs relational IDs so generic Staff Hub can receive tenant-scoped requests. P2.6.4 therefore adds a separate server-only relational authority bridge:

1. `FACTORY_PRODUCTION_LIVE_PILOT` marks an exact factory LIVE revision.
2. `get_factory_production_relational_authority_v1` rechecks the LIVE hotel, active public identity, healthy certification, exact publication pointer, projection state and fail-closed routing resources.
3. It returns only internal room/department/request-routing UUID maps to the server.
4. The authority is attached under a Symbol that survives internal object spreads but is absent from JSON serialization and `Object.keys()`.
5. Guest request inserts can therefore carry `room_id` and `department_id`, enabling generic tenant department Staff Hub without making normalized tables semantic Production authority.

Legacy Production hotels do not have the factory LIVE marker, so their existing runtime path is unchanged.

## Staff access gate

P2.5 introduced arbitrary department role codes in application runtime, but the credential table still contained a legacy four-role database CHECK.

P2.6.4 corrects `staff_access_pins.role` to the same generic role grammar used by the application:
- lowercase letter first;
- then lowercase letters, digits, `_` or `-`;
- maximum 63 characters;
- reserved route segment `pin` is forbidden.

The migration does **not** create, rotate or update any PIN.

A LIVE transition is refused unless:
- an active `manager` PIN exists; and
- every active Production department has an active PIN for its exact department code.

Credentials must therefore be provisioned explicitly before a real activation.

## Operational resources remain fail-closed

P2.6.4 refuses activation if any Production factory shadow resource has been unexpectedly enabled:
- active normalized routing rules;
- runtime-enabled service definitions;
- runtime-enabled workflow definitions;
- configured/non-placeholder integrations;
- runtime-enabled or configured role templates;
- enabled reporting;
- non-placeholder branding/knowledge;
- non-pending AI permissions.

This stage does not invent configuration in order to satisfy the gate.

## Rollback anchor

`factory_production_live_activation_runs` is immutable and stores:
- exact P2.6.3 certification/deployment target;
- activation evidence hash;
- pre-LIVE property lifecycle;
- pre-LIVE hotel active flag;
- pre-LIVE public identity status;
- previous `last_known_good_revision_id`;
- pre-LIVE projection status and metadata;
- pre-LIVE revision validation JSON.

P2.6.5 can therefore restore the exact certified-dark boundary without reconstructing it from assumptions.

## Security

Both P2.6.4 RPCs:
- are server-side only;
- have fixed `search_path = pg_catalog, public`;
- deny execute to public/anon/authenticated;
- allow only `service_role`.

The LIVE mutation additionally requires an authenticated Control Plane `super_admin` or `operator` and same-origin POST.

The activation ledger has RLS enabled. Application service authority receives only `SELECT + INSERT`; no UPDATE/DELETE path exists.

## Explicit non-goals

P2.6.4 does not:
- activate an existing Aquamarine tenant;
- create a fake factory tenant;
- generate staff PINs or other secrets;
- enable operational service/workflow/integration placeholders;
- widen the old M10 Sandbox normalized-runtime activation functions to all Production hotels;
- certify a new runtime revision;
- implement rollback itself (P2.6.5).

## Validation rule for this implementation

Because the current database has zero Product Factory onboarding/publication/certification runs, platform validation must leave:
- all P2.1–P2.6.4 factory run rows at zero;
- activation audit events at zero;
- the existing registry unchanged;
- all Product Factory config/envelope rows at zero.

The LIVE activation RPC must not be invoked merely for testing.
