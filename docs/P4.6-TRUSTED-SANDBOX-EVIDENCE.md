# P4.6 — Trusted Sandbox Evidence Collector

## Status and naming

`P4.6` is a new sequential P4 label introduced after P4.5. It is not a historical milestone name.

P4.6 supplies system-derived evidence for the P2.5 checks that cannot be proven by the P4.5 database-only preflight. It remains read-only and does not call `certify_factory_sandbox_v1`.

## Evidence authority

### Generic Staff runtime

The runtime probe receives the already-authoritative P4.5 preflight object, not a client-provided hotel id.

It derives the exact `sandboxHotelId` and `sandboxRevisionId` from the completed P2.1→P2.4 envelope lineage, reads active departments only for that Sandbox tenant, and resolves every department through the production `resolveStaffRuntimeRoleForHotelId` helper. The manager role is resolved through the same helper.

This intentionally avoids `/staff/[hotelSlug]/...` because pre-certification Sandbox is inactive by contract and public Staff routing correctly refuses inactive hotels.

The probe does not:

- activate Sandbox;
- create a PIN or session;
- create a guest request;
- create a push subscription;
- mutate hotel configuration;
- perform an external write.

The output is deterministic, contains no credential material and is SHA-256 hashed.

### Tenant isolation / canonical CI

P4.6 adds one repository-wide `Factory Release Gate` that runs for every pull request to `main`:

- `npm ci`;
- `npm test`;
- `npm run build`.

Because canonical `npm test` includes the blocking tenant-isolation guard, a successful exact workflow run is the system evidence for the `tenant_isolation` release gate.

The runtime evidence reader uses GitHub's public REST API for this public repository. It does not require a GitHub token and fails closed if the exact workflow run cannot be resolved.

For a Production runtime created by the normal merge process, the current Vercel Git SHA is the merge commit and the second parent is treated as the exact PR candidate SHA. Preview runtime may self-bind directly to its own Git SHA. Unsupported release lineage fails closed.

### Exact Preview build

For that exact candidate SHA, P4.6 reads commit statuses from GitHub and requires the latest `Vercel` status to be `success` with the expected StayHub Vercel project target prefix.

This proves that Vercel itself reported a successful deployment for the same candidate SHA. The target URL is evidence metadata; it is not accepted from the browser.

### Runtime errors

`runtime_errors` deliberately remains `pending`.

A capability experiment proved that Vercel supplies Preview system identity and `VERCEL_OIDC_TOKEN`, but that OIDC token receives HTTP 403 when used as a bearer token against the Vercel management deployment API. Therefore P4.6 does not pretend that runtime logs can be queried secretlessly from the application.

An HTTP 200 smoke is not treated as a substitute for trusted runtime-log evidence.

A later stage must provide an actual trusted Vercel log/error attestation source before P2.5 Sandbox certification can become available.

## Release identity

P4.6 uses only non-secret Vercel system identity fields:

- `VERCEL_ENV`;
- `VERCEL_DEPLOYMENT_ID`;
- `VERCEL_PROJECT_ID`;
- `VERCEL_GIT_COMMIT_SHA`.

The OIDC token is neither read by the production implementation nor returned to the UI.

## UI and mutation boundary

The Factory run workspace shows four external evidence states:

1. Generic Staff runtime;
2. tenant isolation / CI;
3. exact Vercel Preview;
4. runtime error attestation.

There are no operator checkboxes and no certification button in P4.6.

As long as `runtime_errors` is pending, the UI explicitly says that Sandbox certification remains blocked.

## Product Factory safety

P4.6 does not create a Product Factory tenant and does not require a fake tenant for validation. No P2.5 certification run is created during implementation.

Production remains inactive for any future real Product Factory tenant until the later lifecycle stages explicitly permit otherwise.
