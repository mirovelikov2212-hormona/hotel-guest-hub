# P2.3 — Product Factory Operational Resources

Status: **services + workflows + integrations + routing structure gate**

## Goal

P2.3 adds the declarative operational layer to the P2.1/P2.2 tenant envelope
without enabling any guest-facing or staff-execution behavior.

The result is structurally complete enough to describe how a hotel wants to
operate, but still deliberately unpublishable until later certification gates.

## Canonical runtime configuration tables

P2.3 introduces tenant-scoped resources for:

- `hotel_service_definitions` — service key, mode, department/workflow/integration
  relationships, priority and full declarative service metadata;
- `hotel_workflow_definitions` — approved workflow trigger and ordered reusable
  primitive steps;
- `hotel_integration_configs` — adapter metadata and credential-free integration
  placeholders;
- existing `routing_rules` — service request type to normalized department UUID,
  including optional after-hours department.

All new resources belong to a concrete `hotel_id` tenant. Service relational
foreign keys use `(hotel_id, id)` so a service cannot accidentally point to a
department, workflow or integration from another hotel.

## Fail-closed defaults

Factory-created operational resources are structural only in P2.3:

- service `runtime_enabled = false`;
- workflow `runtime_enabled = false`;
- integration `status = placeholder`;
- routing-rule `active = false`;
- Production hotel remains inactive;
- Sandbox hotel remains inactive;
- property remains draft;
- projection status remains `pending`.

No external side effect can be triggered by a P2.3 projection.

## Integration safety

The blueprint remains credential-free. The Product Factory rejects secret-like
keys before persistence, and P2.3 stores only adapter identity/metadata with
`placeholder` status.

Production and Sandbox therefore receive separate placeholder rows, not shared
credentials or live external connections.

## Declarative workflows

Workflow definitions preserve only approved P0 primitive families:

- assign;
- condition;
- approval;
- wait;
- billing;
- notification;
- escalation;
- integration action;
- complete.

Each department and integration reference is validated against resources declared
for the same tenant blueprint. The database RPC independently rechecks those
references before inserting them.

## Routing

Every requestable service that declares a department produces one routing-rule
structure. The route resolves department codes to tenant-specific department UUIDs.
After-hours routing is inherited from the normalized department configuration.

All generated routes start inactive. This allows the structural routing model to
be tested and inspected without making the hotel runnable.

## Revision and lineage

P2.3 requires the exact successful P2.2 core-resource projection. It verifies:

- P2.1 onboarding blueprint hash;
- P2.2 core-resource hash;
- exact Production/Sandbox tenant lineage;
- draft property and inactive environments.

A successful transaction creates immutable revision 3 for both environments.
Validation deliberately remains false with:

- `FACTORY_RUNTIME_CERTIFICATION_PENDING`;
- warning `P2_3_OPERATIONAL_RESOURCES_DISABLED`.

## Idempotency

One P2.3 projection exists per P2.2 core projection.

- same core projection + same operational-resource hash: replay original result;
- same core projection + different hash: `P2_3_IDEMPOTENCY_CONFLICT`.

The transaction never overwrites a partially created resource set.

## Authority

The mutation path remains Control Plane only:

- same-origin POST;
- independent Platform Admin session;
- `super_admin` or `operator` role;
- service-role-only SECURITY DEFINER RPC that rechecks active platform authority;
- Hotel Manager PIN and staff sessions provide no platform authority.

New operational configuration tables are RLS-enabled and unavailable to
`anon`/`authenticated`. Direct service-role mutation is restricted to SELECT +
INSERT; later lifecycle transitions will be performed through explicit audited
functions instead of broad update grants.

## Exit criteria

P2.3 is complete when:

- boutique, resort and portfolio blueprints produce deterministic operational
  resource hashes;
- custom departments survive service/workflow/routing relationships;
- workflow primitive and integration references are validated;
- integrations remain credential-free placeholders;
- all projected execution flags are disabled;
- tenant-isolation review, full contracts and production build pass;
- migrations, RLS, grants, indexes and advisors are verified;
- exact Preview and Production deployments are READY without runtime errors;
- current live hotels and Product Factory registry remain unchanged.

The next stage can add the remaining onboarding envelope — roles, reporting,
branding/knowledge/public identity and health/certification state — before any
factory-created hotel is allowed to become runnable.
