# P2.5 — Sandbox Certification / Generic Staff Runtime Gate

## Status and purpose

P2.5 removes the fixed four-department Staff Hub assumption from the Product Factory runtime boundary and adds an explicit, audited Sandbox certification transition. It does not publish or activate a factory Production hotel.

The P0 rule remains authoritative: a hotel is tenant data/configuration in the shared runtime, not a separate codebase or deployment.

## Generic Staff runtime

Tenant department codes use the same constrained lowercase key contract as `departments.code`. `manager` remains a special control role; every other operational role must resolve to an active department belonging to the requested hotel.

The runtime gate now covers:

- generic role parsing and staff session cookie keys;
- hotel-scoped active department resolution;
- PIN login for arbitrary configured departments;
- dynamic `/staff/[hotelSlug]/[departmentCode]` fallback pages;
- tenant- and department-scoped request reads and status mutations;
- generic staff QR routing;
- generic push subscription authorization;
- sound and inactive-tab alerts;
- generic labels and fallback UI.

Aquamarine's specialized `reception`, `housekeeping`, `maintenance`, and `manager` pages remain in place. The generic dynamic route deliberately excludes those role keys so P2.5 does not replace stable hotel-specific operating behavior.

No staff authority is derived from a URL segment alone. A custom department route is valid only when the hotel is active and an active department with that exact code exists for that hotel. Mutations additionally verify the request hotel and its department ownership.

## Sandbox certification transition

Database authority is `certify_factory_sandbox_v1` and the immutable ledger is `factory_sandbox_certification_runs`.

Certification requires:

1. an active Platform Admin with mutation authority;
2. exact P2.4 envelope → P2.3 operational → P2.2 core → P2.1 onboarding lineage;
3. exact draft revision 4 for both reserved Production and Sandbox tenants;
4. Production inactive and non-sandbox;
5. Sandbox inactive, marked sandbox, and linked to its Production tenant;
6. active Sandbox departments covered by fail-closed department role templates;
7. all Product Factory role templates runtime-disabled with no configured permissions;
8. services and workflows runtime-disabled, routing inactive, and integrations still placeholders;
9. reporting disabled with no recipients;
10. branding and knowledge still explicit placeholders;
11. AI permissions pending with every action false;
12. Production and Sandbox public identities still reserved and health/certification not started;
13. explicit evidence gates for generic staff runtime, tenant isolation, Preview build, runtime error check, Supabase security, integrations, reporting, branding, and knowledge.

On a successful transition the transaction may change only Sandbox certification state: Sandbox health becomes healthy/passed, its reserved identity becomes certified, its revision validation becomes successful, certification evidence is recorded, and the Sandbox hotel becomes active for the certification runtime. Production remains inactive, identity status `reserved`, and certification `not_started`; the function re-checks those invariants before committing.

The transition is idempotent for an exact envelope projection run plus exact evidence/check payload. A different replay conflicts instead of silently changing certification evidence.

## Control Plane entrypoint

`POST /api/control-plane/onboarding/sandbox-certification` is the application entrypoint. It requires the existing Platform Admin session and same-origin guard, computes a deterministic SHA-256 evidence hash, and delegates to the service-role-only certification RPC.

The endpoint is intentionally not a Production publication API. P2.5 has no path that changes a factory Production hotel to active/certified/published.

## Database access model

`factory_sandbox_certification_runs` has RLS enabled. `anon` and `authenticated` receive no table access. `service_role` receives only `SELECT` and `INSERT`; no `UPDATE` or `DELETE` grant is present.

`certify_factory_sandbox_v1` is `SECURITY DEFINER`, pins `search_path` to `pg_catalog, public`, and grants `EXECUTE` only to `service_role` (plus database owner authority).

## Non-goals

P2.5 does not:

- create a fake hotel for testing;
- create department credentials automatically;
- configure role permissions automatically;
- activate services/workflows/routing automatically;
- configure third-party integrations automatically;
- enable reporting recipients;
- replace Aquamarine-specific operating pages;
- activate or publish a factory Production hotel.

A separate, audited publication/activation stage is required after a real factory tenant has passed Sandbox certification.
