# P4.7 — Vercel Runtime Log Attestation Foundation

## Status and naming

`P4.7` is a new sequential P4 label introduced after P4.6. It is not a historical milestone name.

P4.7 creates the trusted ingestion/storage foundation needed for the still-pending P2.5 `runtime_errors` evidence gate. This stage does **not** mark `runtime_errors` as validated and does not call `certify_factory_sandbox_v1`.

## Why the receiver is outside Vercel

The receiver is a Supabase Edge Function, not a route in the StayHub Vercel project. Sending the project's own Log Drain back into the same project can create self-observation/feedback behavior and would make the evidence boundary harder to reason about.

The external receiver is:

`supabase/functions/vercel-runtime-log-drain`

It requires Vercel's `x-vercel-signature` HMAC-SHA1 signature. If `VERCEL_LOG_DRAIN_SECRET` is absent, the function fails closed with `drain_not_configured`. The shared signing secret is platform infrastructure and must never be stored in Product Factory hotel data, committed to Git, returned to the UI, or invented during validation.

## Privacy-minimal event model

Vercel's Log Drain schema can contain log messages, request metadata and other information not needed by Product Factory certification. P4.7 therefore persists only qualifying evidence:

- `error` level logs;
- `fatal` level logs;
- HTTP 5xx runtime events;
- StayHub-owned structured Factory smoke markers.

Raw Vercel log messages are never persisted. The receiver computes SHA-256 over the message and stores only the digest plus bounded technical metadata:

- Vercel log id;
- Vercel project id;
- deployment id;
- Preview/Production environment;
- event timestamp;
- event kind / level / source;
- bounded host/path;
- status code;
- message SHA-256;
- validated smoke-marker lineage fields where applicable.

Requests from any other Vercel project id are ignored by the normalizer.

## Immutable ledger

Database table:

`factory_vercel_runtime_log_events`

Security properties:

- RLS enabled;
- no anon/authenticated access;
- service role receives only `SELECT` and `INSERT`;
- no `UPDATE` or `DELETE` grant;
- Vercel log id is the primary key, making delivery retries idempotent.

Batch ingest RPC:

`ingest_factory_vercel_runtime_log_batch_v1(jsonb)`

The RPC is `SECURITY DEFINER`, uses fixed `search_path = pg_catalog, public`, is executable only by service role, validates every normalized field, caps a batch at 500 events and inserts with `ON CONFLICT DO NOTHING`.

## Smoke observation windows

Read RPC:

`get_factory_vercel_runtime_log_window_v1(deploymentId, smokeRunId)`

A future exact Preview smoke will emit three structured markers from the same deployment and exact envelope lineage:

1. `start`
2. `end`
3. `settle`

The settle marker must be at least 60 seconds after the end marker. The read RPC fails closed on missing, duplicate or inconsistent marker lineage and counts `error`, `fatal` and `http_5xx` evidence in the exact deployment window.

A clean result is deliberately named:

`observed_clean`

not `validated`.

Its response explicitly carries:

`evidenceSemantics = observed_drain_window_not_p2_5_validation`

This prevents the foundation from silently weakening the P2.5 certification contract before live Drain delivery, signature verification, exact Preview smoke and delivery/completeness behavior have been proven.

## What remains before runtime_errors can validate

P4.7 does not configure a real Vercel Drain because the current connected Vercel tool surface does not expose Drain creation/secret management, and no shared secret may be invented.

The later activation step must prove all of the following with a real platform-level configuration:

- a Vercel Drain scoped to the StayHub project;
- a real shared signing secret stored only in platform secret stores;
- successful Vercel delivery/signature verification to the Supabase Edge Function;
- exact Preview smoke markers linked to the P2.4 envelope and exact candidate Git SHA/deployment;
- a settled observation window;
- comparison/verification sufficient to treat drain-backed absence of errors as trusted evidence.

Until then P4.6 continues to report `runtime_errors = pending`, and P2.5 Sandbox certification remains blocked.

## Product Factory safety

P4.7 does not:

- create a fake Product Factory tenant;
- create a Sandbox certification run;
- activate Sandbox;
- activate or publish Production;
- store raw logs or hotel credentials;
- change P2.5 required checks;
- create or invent a Vercel token or Log Drain secret.
