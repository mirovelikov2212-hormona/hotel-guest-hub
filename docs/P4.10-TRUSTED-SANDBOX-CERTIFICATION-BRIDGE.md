# P4.10 — Trusted Sandbox Certification Bridge

## Purpose

P4.10 removes caller-supplied certification booleans and evidence from the P2.5 Sandbox Certification browser boundary.

The Control Plane caller supplies only the exact P2.4 `envelopeProjectionRunId` and the exact P4.8 `smokeRunId`. The server derives all nine P2.5 required checks from the existing trusted evidence stack before delegating to the existing P2.5 mutation service.

P4.10 does not create a Product Factory tenant, does not invent a smoke run, and does not manufacture certification evidence.

## Trusted evidence chain

The bridge requires all of the following at the moment certification is requested:

1. **P4.5 database preflight**
   - exact P2.1 → P2.4 lineage;
   - database status validated;
   - Production inactive;
   - Sandbox inactive;
   - certification not started;
   - Supabase security, integration placeholders, reporting fail-closed, branding placeholder, and knowledge placeholder validated.

2. **P4.6 release evidence**
   - current runtime is Vercel Preview;
   - lineage mode is `preview_self`;
   - canonical Factory Release Gate validated;
   - exact Vercel Preview status validated;
   - tenant-isolation and preview-build checks validated.

3. **Current Generic Staff runtime probe**
   - exact Sandbox hotel and revision from P4.5;
   - manager and all active tenant departments resolve correctly;
   - probe status validated.

4. **P4.8 / P4.7 signed runtime observation**
   - exact envelope and smoke run;
   - same exact Preview deployment as the P4.6 runtime identity;
   - `observed_clean` status;
   - exactly three signed markers (`start`, `end`, `settle`);
   - zero `error`, `fatal`, or HTTP `5xx` evidence in the window;
   - exact project, deployment, Git SHA, envelope and smoke lineage.

Only after all four evidence layers pass does P4.10 derive all nine P2.5 checks as `true` and call the existing `certifyFactorySandbox` service. The underlying `certify_factory_sandbox_v1` RPC remains the sole database certification authority and rechecks its own lineage and fail-closed invariants.

## Browser boundary

`POST /api/control-plane/onboarding/sandbox-certification` accepts only:

- `envelopeProjectionRunId`
- `smokeRunId`

Caller-provided `checks` or `evidence` are explicitly rejected. Unknown body fields are rejected as well.

The route remains same-origin and Platform Admin authenticated.

## Evidence persisted by P2.5

The certification evidence passed to the existing P2.5 mutation contains only system-derived provenance:

- P4.5 environment/revision lineage;
- P4.6 release evidence hash and exact deployment/Git identifiers;
- Generic Staff probe evidence hash and department count;
- P4.8/P4.7 clean-window summary and timestamps.

No raw Vercel log message, credential, PIN, Vercel signing secret, or Supabase service-role key is included.

## Fail-closed boundaries

P4.10 refuses certification when any of these are true:

- no real P2.4 envelope exists;
- Production or Sandbox state changed;
- certification already started;
- a database check is not validated;
- current runtime is not the exact validated Preview;
- Factory Release Gate or Vercel Preview evidence is not validated;
- Generic Staff runtime is not validated;
- smoke markers are missing, ambiguous, from another deployment/SHA/envelope, or contain a blocking runtime event.

P4.10 never calls P4.8 `start` or `settle`; it consumes an already completed real smoke run. This prevents the certification bridge from manufacturing its own evidence.

## Activation boundary

A successful P2.5 certification intentionally activates the **Sandbox hotel only**, according to the existing P2.5 RPC contract. Production remains inactive/reserved. P4.10 does not publish, certify, or activate Product Factory Production.

At introduction time there are no real Product Factory P2.1–P2.4 onboarding runs to certify, so P4.10 is validated by contracts and Preview only. No fake tenant or fake certification run is created for demonstration.
