# P4.4 — Guided Resource Projection Workspace

Status: **resume-safe P2.2 → P2.3 → P2.4 operator orchestration**

## Goal

P4.4 turns a completed P4.3 draft foundation into a resumable Control Plane workflow for the next three Product Factory projection stages:

1. P2.2 core resources;
2. P2.3 operational resources;
3. P2.4 onboarding envelope.

The stages remain separate audited transactions. P4.4 never auto-chains them.

## Resume-safe progress

A service-role-only `STABLE` read RPC reconstructs Product Factory progress from the immutable predecessor ledgers:

`factory_onboarding_runs → factory_core_resource_projection_runs → factory_operational_resource_projection_runs → factory_onboarding_envelope_projection_runs`.

Each predecessor relationship is already unique in the database. The progress read therefore has one unambiguous current state.

The read also returns the authoritative P2.1 `blueprint_json`, current Property lifecycle and actual Production/Sandbox `hotels.active` values.

## Factory runs

The Control Plane gets:

- a bounded list of the latest 50 Factory onboarding runs;
- one BG/EN detail workspace per `onboardingRunId`;
- links back to the new-hotel blueprint workspace.

Refreshing or reopening a run does not depend on browser state.

## Projection actions

The detail workspace uses the existing P2 APIs:

- foundation `onboardingRunId` → `/api/control-plane/onboarding/core-resources`;
- core `projectionRunId` → `/api/control-plane/onboarding/operational-resources`;
- operational `projectionRunId` → `/api/control-plane/onboarding/envelope`.

Every action submits the immutable blueprint stored in the P2.1 run. The operator never re-enters lineage IDs.

After each successful action `router.refresh()` reloads authoritative database state.

## Fail-closed guard

P4.4 allows projection buttons only while the actual foundation remains:

- Property lifecycle `draft`;
- Production hotel inactive;
- Sandbox hotel inactive.

The P2 database RPCs independently recheck their own exact lineage and fail-closed invariants.

## No automatic runtime activation

P4.4 stops after the onboarding envelope. It does not invoke Sandbox certification, Production readiness/publication/runtime certification, LIVE activation or the P3 commercial lifecycle.

P2.2 rooms/departments remain structural, P2.3 services/workflows/routing remain disabled/placeholder, and the P2.4 envelope remains pending/fail-closed.

## Validation boundary

No fake Product Factory tenant is created for P4.4 validation. The read RPC is rehearsed inside a database transaction and rolled back. After CI/Preview passes, the read-only migration may be applied; with zero Factory runs it must return an empty list.

No P2.2/P2.3/P2.4 POST is sent during validation because no disposable onboarding lineage exists.
