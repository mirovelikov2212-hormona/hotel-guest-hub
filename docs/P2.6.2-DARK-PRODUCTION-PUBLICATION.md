# P2.6.2 — Dark Production Configuration Publication

## Goal

P2.6.2 introduces the audited transaction that publishes the exact Product Factory Production configuration revision after P2.6.1 readiness, while deliberately keeping the Production tenant dark.

This stage is **configuration publication only**. It is not the LIVE switch.

## Required preconditions

The transaction requires:

- an immutable P2.6.1 readiness run with status `ready`;
- the exact expected Production hotel id and revision id from that readiness run;
- the exact reserved Production public slug;
- an active Platform Admin with mutation authority;
- exact P2.1 → P2.6.1 lineage;
- certified and active linked Sandbox;
- Production hotel still inactive and non-sandbox;
- Production property lifecycle still `draft`;
- Production public identity still `reserved`;
- Production health certification still `pending / not_started`;
- Production revision still the exact draft factory revision 4;
- Production runtime services, workflows, roles and routing still disabled;
- integrations still placeholders.

## Explicit approval contract

The server accepts publication only when the caller explicitly supplies the fixed approval shape:

- `publishConfiguration: true`
- `keepProductionDark: true`
- `requireRuntimeCertification: true`
- `activateHotel: false`
- `activatePublicIdentity: false`

The canonical approval payload is SHA-256 hashed and recorded in the immutable publication ledger.

## Transaction

`publish_factory_production_revision_v1` uses an advisory lock and row locks, revalidates the complete factory lineage and exact expected targets, then performs only these Production changes:

1. marks the exact revision 4 as `published` and validation-ok with a warning that runtime certification is still pending;
2. points `hotel_config_publication_state.published_revision_id` at that exact revision;
3. records projection metadata that the config is published, runtime certification is pending, public activation is false, and Production remains dark;
4. writes an immutable `factory_production_publication_runs` ledger row;
5. writes a Control Plane audit event.

Before commit it reasserts that the Production hotel is still inactive, public identity is still reserved, certification is not started, property lifecycle is still draft, and runtime resources remain disabled.

## Deliberate non-actions

P2.6.2 does **not**:

- set `hotels.active=true`;
- activate public or QR identity;
- change the property to pilot/active;
- certify Production runtime;
- enable service/workflow/role runtime;
- activate routing rules;
- configure integrations or credentials;
- create PINs or secrets;
- call the legacy `publish_hotel_config_revision`, which requires an already-active hotel;
- create a test/fake factory tenant.

## P2.6.1 lineage correction

During P2.6.2 analysis we found that the initial P2.6.1 readiness RPC compared P2.3 revision ids to P2.2 revision ids for equality. P2.2 intentionally creates revision 2 and P2.3 intentionally creates revision 3, so a real first factory readiness run would have failed.

`20260817141000_p2_6_1_readiness_lineage_fix.sql` corrects this latent gate by validating each revision against its intended stage and revision number instead of equating different-stage revision ids. The correction is guarded against source drift and preserves the same service-role-only security boundary.

## Next boundary

After a successful P2.6.2 dark publication, the tenant remains inaccessible as a Product Factory Production hotel. P2.6.3 must separately certify the published Production runtime before any LIVE/public activation stage can exist.
