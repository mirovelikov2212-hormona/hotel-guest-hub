# P3.1 — Commercial Lifecycle & Trial Engine

## Goal

Add a commercial authority layer to StayHub Control Plane without changing the technical Product Factory lifecycle.

Technical lifecycle remains:

`Sandbox → certified → Production readiness → dark publish → runtime certification → LIVE → rollback`

Commercial lifecycle is independent:

`pending → trial → active_customer → suspended → ended`

A trial is a real hotel tenant using the normal service. It is not a separate demo codepath.

## Why separate technical and commercial state

`properties.lifecycle_state` describes technical runtime state. It must not be overloaded with sales, contract, billing or trial semantics.

P3.1 introduces `property_commercial_state` as the commercial source of truth. Existing hotels receive no row automatically and therefore remain `UNMANAGED / LEGACY`. This prevents a migration from changing Aquamarine, Demo or certification environments.

## Trial semantics

- Trial duration is explicit and configurable per hotel.
- Initial trial is limited to 1–60 days.
- The common sales flow can use 14 days.
- Trial expiry is derived from `trial_ends_at`; no cron is required to change the state row.
- `trial` + current time before `trial_ends_at` => `trial_active`, access entitled.
- `trial` + current time at/after `trial_ends_at` => `trial_expired`, access not entitled.
- Trial can be extended to an explicit future date, with a 180-day total safety ceiling.
- Conversion to `active_customer` preserves the same property, Production hotel, data, config and identities.
- P3.1 does not directly deactivate `hotels.active` when a trial expires. Runtime enforcement belongs to the later Control Plane orchestration layer.

## State transitions

### initialize
Creates the first `pending` commercial state. This can happen before Production is LIVE.

### start_trial
`pending → trial`

Requires:
- property technical lifecycle `pilot` or `active`
- active Production environment
- Production hotel is neither sandbox nor demo
- exact optimistic version
- 1–60 trial days

### extend_trial
`trial → trial`

Requires a later explicit trial end and keeps the total trial window within 180 days.

### convert_to_customer
`pending | trial | suspended → active_customer`

Requires:
- active Production runtime
- explicit plan code
- exact optimistic version

This allows both trial conversion and a direct contract without a trial.

### suspend
`trial | active_customer → suspended`

Commercial access becomes not entitled. The previous status is retained for safe resume.

### resume
`suspended → trial | active_customer`

Trial resume is rejected if the trial has already expired. Customer resume requires an existing contract start.

### end
Any non-ended managed commercial state can become `ended`.

## Safety

- No migration backfill.
- No existing tenant changes.
- No direct writes to `hotels` or `properties`.
- Commercial mutations are scoped to one exact `property_id`.
- Active Platform Admin `super_admin` or `operator` only.
- same-origin Control Plane API.
- service-role-only `SECURITY DEFINER` RPC with fixed `search_path`.
- RLS enabled on both commercial tables.
- immutable lifecycle event ledger.
- UUID idempotency key + SHA-256 canonical request hash.
- optimistic version compare-and-swap.
- idempotent replay only if the resulting state is still exact.
- drift fails closed.
- audit entry written for every successful transition.

## Tables

### `property_commercial_state`
Current commercial authority for one property.

### `property_commercial_lifecycle_events`
Immutable event ledger and idempotency history.

## Control Plane read model

The registry now displays both:

- technical lifecycle
- commercial lifecycle

Existing rows without P3 state appear as `UNMANAGED / LEGACY`.

Top-level metrics add:

- Commercial managed
- Active trials
- Customers

## Scope boundary

P3.1 creates commercial authority and a transition API.

It deliberately does not yet:
- automatically start a trial during P2.6.4 LIVE activation
- automatically block Guest/Staff runtime when a trial expires
- generate contracts
- charge cards or integrate a payment provider
- create invoices
- send trial-expiry emails
- mutate existing hotels into commercial management

Those are later P3 orchestration, entitlement enforcement and billing phases.
