# P2.2 — Product Factory Core Resources

Status: **rooms + departments projection gate**

## Goal

P2.2 turns the P2.1 tenant envelope into concrete, tenant-isolated room and
department resources while keeping both Production and Sandbox fail-closed.

A new hotel still cannot be published or activated in this stage.

## Room inventory

The factory blueprint now supports concrete inventory as configuration rather
than assuming a numbering scheme.

Two reusable forms are supported:

- explicit rooms, including non-numeric identifiers such as `A-01` or `PH`;
- generated numeric ranges with configurable prefix, suffix and zero-padding.

Ranges are blueprint data. The platform does not infer hotel numbering from the
room count.

The expanded inventory must:

- contain 1–10,000 rooms;
- match the declared `property.roomCount`;
- contain unique non-empty room numbers;
- contain at least one active room.

## Generic department keys

The original normalized schema used a PostgreSQL enum for department codes. That
was suitable for the first hotel but violated the P0 Product Factory contract:
a resort blueprint already requires custom departments such as `pool` and
`guest-relations`.

P2.2 changes `departments.code` to constrained text while preserving:

- `(hotel_id, code)` uniqueness;
- tenant-safe UUID relationships from routing rules;
- the old `department_code` enum itself for backward compatibility;
- the current M10 legacy projector's conservative standard-department behavior.

Valid factory department keys are lowercase tenant configuration keys using
letters, digits, `_` and `-`.

## Production / Sandbox projection

One successful `project_factory_core_resources_v1` transaction:

1. locks and verifies the P2.1 onboarding run;
2. rechecks active Platform Admin mutation authority;
3. verifies the property is still draft and both hotel environments inactive;
4. verifies Production/Sandbox registry linkage;
5. inserts the same room inventory into both isolated hotel tenants;
6. inserts the same standard or custom department configuration into both;
7. creates immutable configuration revision 2 for Production and Sandbox;
8. records both projection-state rows as `pending`;
9. records an immutable core-resource projection run;
10. appends a Control Plane audit event.

## Fail-closed state

Revision 2 remains `draft` and intentionally has:

- `ok = false`;
- error `FACTORY_SERVICES_WORKFLOWS_NOT_PROJECTED`;
- warning `P2_2_CORE_RESOURCES_ONLY`.

`hotel_config_projection_state` remains `pending` with routing counts equal to
zero. No hotel activation, property lifecycle promotion or publication state
change occurs.

This is deliberate: rooms and departments alone are not a runnable StayHub
configuration.

## Idempotency

The P2.2 projection has one immutable run per P2.1 onboarding run and a
deterministic SHA-256 hash of normalized core resources.

- same onboarding run + same hash: returns the original projection and revision
  IDs with `replayed = true`;
- same onboarding run + different hash: fails with `P2_2_IDEMPOTENCY_CONFLICT`.

A partially configured duplicate cannot silently overwrite room or department
inventory.

## Authority boundary

The mutation path remains Control Plane only:

- same-origin POST;
- independent Platform Admin session;
- `super_admin` or `operator` role;
- service-role-only database RPC that rechecks the active admin;
- Hotel Manager PIN and staff sessions have no authority.

## P2.2 exit criteria

P2.2 is complete when:

- P0 stress fixtures contain concrete room inventory;
- arbitrary room identifiers and configured ranges pass contracts;
- custom department keys such as `pool` and `guest-relations` survive the
  normalized model and database schema;
- existing M10 projection compatibility is preserved;
- P2.2 transaction contracts prove idempotency and fail-closed behavior;
- tenant-isolation review, full contracts and production build pass;
- migrations are applied and RLS/grants/advisors are verified;
- exact Preview and Production deployments are READY without runtime errors;
- the existing live hotels and Product Factory registry remain unchanged.

After this gate, P2.3 can add services, workflows, routing and integration
placeholders before any Sandbox certification or publication is possible.
