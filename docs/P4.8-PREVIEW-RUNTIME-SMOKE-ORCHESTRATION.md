# P4.8 — Preview Runtime Smoke Orchestration

## Purpose

P4.8 connects the P4.6 trusted Preview/release evidence and the P4.7 signed Vercel Runtime Log Drain into an exact, Preview-only observation window for a real Product Factory onboarding envelope.

This phase does **not** create a Product Factory tenant, does **not** activate Sandbox, does **not** activate Production, and does not call the P2.5 certification mutation.

## Preconditions

A smoke run can start only when all of the following are true:

- the caller is authenticated as Platform Admin through the same-origin Control Plane route;
- a real P2.4 envelope projection run exists and resolves through the P4.5 server-side preflight;
- the preflight database gates are validated;
- Production and Sandbox are both still inactive and certification has not started;
- the current Vercel runtime is `preview`;
- the exact Preview deployment, Vercel project and Git SHA are available from system runtime identity;
- the P4.6 Factory Release Gate and exact Vercel Preview evidence are validated for that same SHA.

Caller-provided deployment IDs, project IDs and Git SHAs are never trusted as smoke authority.

## Observation lifecycle

`POST /api/control-plane/onboarding/sandbox-runtime-smoke` accepts three explicit actions.

### `start`

The server generates the `smokeRunId`, emits the P4.7 `start` marker, executes the existing read-only Generic Staff runtime probe against the exact Sandbox hotel resolved from the P2.4 envelope, then emits the `end` marker.

No guest request, PIN flow, hotel activation or Factory lifecycle mutation is performed.

### `settle`

Settlement reads the signed marker evidence already received by the P4.7 Vercel Drain ledger. The exact deployment/project/environment/envelope/Git lineage must match and there must be exactly one `start` and one `end` marker. P4.8 waits at least 60 seconds after the observed `end` marker before emitting `settle`.

If signed marker delivery is delayed, the action returns a waiting state instead of guessing. Ambiguous or conflicting marker evidence fails closed.

### `status`

Status reads `get_factory_vercel_runtime_log_window_v1` for the exact deployment and smoke run. P4.7 counts any `error`, `fatal`, or HTTP `5xx` event between `start` and `settle` and validates the three-marker lineage.

The P4.7 clean state remains `observed_clean` and carries the explicit evidence semantics `observed_drain_window_not_p2_5_validation`.

## P2.5 boundary

P4.8 intentionally returns:

`runtime_errors = PENDING`

Even if the signed observation window is clean, this phase does not submit that result to `certify_factory_sandbox_v1` and does not turn the P2.5 check true by itself. A real P2.4 envelope is required before a tenant-specific smoke can even be started, and the subsequent certification stage must explicitly consume validated evidence under its own exact-lineage rules.

At the time P4.8 was introduced, the Product Factory lifecycle contained no real P2.1–P2.4 onboarding runs. Therefore no fake envelope or fake tenant is created merely to demonstrate the smoke path.

## Security and isolation properties

- Preview-only runtime identity; Production execution fails closed.
- Same-origin Control Plane + authenticated Platform Admin.
- Exact server-derived P2.4 envelope lineage.
- Exact server-derived Vercel deployment/project/Git identity.
- Existing P4.6 read-only Generic Staff probe; no activation required.
- Signed P4.7 Drain evidence is used for marker timing and status.
- No Vercel signing secret is exposed to the application route or Product Factory data.
- No raw runtime log messages are persisted by the P4.7 evidence ledger.
- No Product Factory lifecycle mutation is performed by P4.8.
