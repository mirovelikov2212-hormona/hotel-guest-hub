# P2.6.3 — Production Runtime Certification

## Goal

P2.6.3 certifies the exact Product Factory Production revision that was dark-published by P2.6.2, without making the tenant LIVE.

The stage answers one question:

> Is this exact published Production configuration, on this exact application deployment, ready to enter a later LIVE activation transaction?

A successful certification is therefore **pre-activation evidence**, not activation itself.

## Why certification stays dark

The real Guest runtime resolves hotel identity through active-hotel lookups. Both `getHotelByAnySlug()` and `getHotelSheetSources()` require `hotels.active=true`.

P2.6.3 deliberately does not weaken or bypass that public safety boundary. A factory Production hotel remains inaccessible through normal Guest/QR/Staff runtime until a later audited activation stage.

Instead, P2.6.3 requires exact deployment evidence plus database revalidation of the same published configuration and normalized resources that LIVE runtime will consume.

## Required evidence gates

The Control Plane service accepts certification only when every required check is explicitly `true`:

- `exact_production_deployment`
- `published_config_runtime`
- `guest_runtime_contract`
- `qr_runtime_contract`
- `generic_staff_runtime`
- `normalized_room_runtime`
- `normalized_department_routing`
- `tenant_isolation`
- `supabase_security`
- `runtime_logs`
- `public_route_fail_closed`
- `runtime_resources_fail_closed`
- `no_production_activation`

The caller must also provide:

- exact P2.6.2 publication run id;
- exact expected Production hotel id;
- exact expected Production revision id;
- exact Vercel deployment id;
- exact 40-character Git commit SHA;
- structured evidence;
- explicit approval that certification must remain dark.

The canonical certification payload is SHA-256 hashed and stored in the immutable ledger.

## Explicit no-activation approval

The server accepts the mutation only with this exact approval intent:

- `certifyRuntime: true`
- `keepProductionDark: true`
- `activateHotel: false`
- `activatePublicIdentity: false`
- `enableRuntimeResources: false`

This makes an accidental LIVE transition incompatible with the P2.6.3 API contract.

## Database transaction

`certify_factory_production_runtime_v1` is service-role-only, `SECURITY DEFINER`, and uses a fixed `search_path`.

It revalidates:

1. active Platform Admin mutation authority;
2. immutable P2.6.2 publication run;
3. exact Production hotel/revision target;
4. exact P2.1 → P2.6.2 lineage;
5. linked certified/active Sandbox;
6. Production hotel still inactive and non-sandbox;
7. property lifecycle still `draft`;
8. exact published factory revision 4;
9. exact publication-state pointer with no last-known-good revision yet;
10. Production public identity still `reserved`;
11. Production health still `pending / not_started`;
12. exact projection metadata from P2.6.2;
13. normalized room/department/routing counts equal current relational rows;
14. Production/Sandbox room and department parity;
15. generic department/manager role templates remain configured fail-closed;
16. services, workflows, routing and integrations remain disabled/placeholders;
17. reporting, branding, knowledge and AI permissions remain fail-closed.

Only after all gates pass does the transaction:

- set Production health to `healthy / passed`;
- bind health certification to the exact published Production revision;
- record the exact deployment id/SHA and evidence hash in health checks;
- change Production public identity from `reserved` to `certified`;
- mark the published revision as `FACTORY_PRODUCTION_RUNTIME_CERTIFIED_DARK`;
- record projection metadata `runtimeCertification=passed`;
- write an immutable `factory_production_runtime_certification_runs` row;
- write a Control Plane audit event.

## Deliberate non-actions

P2.6.3 does **not**:

- set `hotels.active=true`;
- set public identity to `active`;
- change the property lifecycle;
- enable services;
- enable workflows;
- enable role runtime;
- activate routing rules;
- configure credentials or integrations;
- create staff PINs or secrets;
- set projection state to `ready`;
- create or persist a fake Product Factory tenant;
- invoke the certification RPC merely for platform testing.

After successful P2.6.3, the intended state is:

- Production config: published;
- Production runtime certification: passed;
- public identity: certified;
- hotel: inactive;
- public routes: still fail-closed;
- operational runtime: still disabled;
- property: draft.

## Idempotency and drift

Each P2.6.2 publication run can have only one P2.6.3 certification row.

A replay succeeds only if deployment id, deployment SHA, evidence hash, checks and exact target are identical. A conflicting replay fails.

Even an identical replay fails if the certified dark state has drifted.

## Next boundary

P2.6.3 creates a certified-dark Production candidate. A later stage may implement the atomic LIVE activation switch, using this immutable certification run as its only acceptable predecessor.

That LIVE switch is outside P2.6.3.
